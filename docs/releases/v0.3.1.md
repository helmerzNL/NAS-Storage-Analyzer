## 🐛 Opgelost

- **Een SMB-share door de worker laten mounten mislukte altijd** (#37). Gemeld op Home Assistant; de scan eindigde met `scan.failed` en `Unable to set current process capabilities: Operation not permitted`. `mount.cifs` zet bij de start zelf zijn rechten en vraagt daarvoor `CAP_SYS_ADMIN`, `CAP_DAC_READ_SEARCH` en `CAP_DAC_OVERRIDE`; mist er één, dan stopt hij voordat er iets gemount wordt. Docker's standaardset heeft `CAP_DAC_OVERRIDE` maar niet `CAP_DAC_READ_SEARCH`, en de Compose-worker laat alle rechten vallen, dus een container met alleen `SYS_ADMIN` erbij, zoals de handleiding zei, kon nooit SMB mounten. Nu geeft `docker-compose.mounts.yml` de worker alle drie, noemt de foutmelding de ontbrekende rechten in plaats van naar een override te verwijzen die je al gebruikt, en waarschuwt het all-in-one image in de log als er rechten ontbreken. NFS had hier geen last van.
  - **Wat getest is:** met de echte `mount.cifs` van het image (Alpine 3.20, `cifs-utils` 7.0) komt de mount voorbij zijn rechtencontrole met de rechten uit het override-bestand en niet met `SYS_ADMIN` alleen; CI controleert dat bij elke build. **Niet getest** is een echte SMB-server of een echte Home Assistant-installatie; of de mount daarna slaagt hangt van server, versie en inloggegevens af, en op hosts met AppArmor kan de mount zelf nog geblokkeerd worden (zie *Bijwerken*). Test een nieuwe share met *Scan nu*.

Elk van die controles faalt als je een recht weghaalt (#37).

## ⚠️ Bijwerken

- **Draai je `0.2.0` of `0.3.0` en laat je de worker geen NFS/SMB mounten?** Dan is er niets te doen: er verandert niets aan `docker-compose.yml`, `.env.example` of de database, en er zijn geen nieuwe migraties. Haal de image op (`docker compose pull`, daarna `docker compose up -d`; *Redeploy* in een stackbeheerder haalt een bewegende tag niet vanzelf op).
- **Gebruik je `docker-compose.mounts.yml` (de worker mount zelf)?** Haal de nieuwe versie van dat bestand op en maak de worker opnieuw aan met `docker compose -f docker-compose.yml -f docker-compose.mounts.yml up -d`. Heb je een eigen kopie, voeg dan onder `worker.cap_add` `DAC_READ_SEARCH` en `DAC_OVERRIDE` toe naast `SYS_ADMIN`. Zonder die twee blijft SMB falen; NFS werkte al.
- **Draai je het all-in-one image of een container met `docker run` (Unraid, Portainer, Home Assistant) en wil je dat de worker SMB mount?** Geef de container `--cap-add SYS_ADMIN --cap-add DAC_READ_SEARCH`; Docker's standaardrechten blijven staan, dus `DAC_OVERRIDE` hoeft niet apart. Waar AppArmor de mount blokkeert komt `--security-opt apparmor=unconfined` erbij. De veiligere route blijft: de share op de host mounten en alleen-lezen doorgeven (zie [`docs/deploy.md`](../deploy.md#2-shares-beschikbaar-maken)).
- **Kom je van vóór `0.2.0`?** Doe dan eerst de bijwerkstappen van [`v0.2.0.md`](v0.2.0.md) (de kop *Bijwerken*). In het kort: maak een back-up (de migraties `0005`, `0006` en `0007` zijn niet terug te draaien), hernoem de variabelen met `sed -i 's/^NASA_/NASSA_/' .env` (een oude `.env` wordt geweigerd), verplaats de database van het volume `db-data` naar een absolute map `DATA_PATH` met `scripts/migrate_data.sh`, en vervang je `docker-compose.yml` door die van deze versie.
- **Wil je het all-in-one image proberen?** Zie [`docs/deploy.md` §8b](../deploy.md#8b-all-in-one-image-unraid-store-en-home-assistant). Het pakket `nas-storage-analyzer-aio` moet op GHCR mogelijk eenmalig openbaar gemaakt worden voordat Unraid of Home Assistant het zonder inloggen kan ophalen.

# 🇬🇧 English

## Highlights

**Letting the worker mount an SMB share now works.** It always failed with `Unable to set current process capabilities: Operation not permitted`, because the guide and `docker-compose.mounts.yml` gave the worker too few privileges. If you mounted your shares on the host and added them as a path (the recommended route), you were never affected.

Everything from [`v0.2.0.md`](v0.2.0.md) and [`v0.3.0.md`](v0.3.0.md) is in as well: install and update without building, invite with a link, backup and restore in the app, delete scripts for files and folders, an audit log that keeps every scan outcome, and the all-in-one image for Unraid and Home Assistant.

## ✨ New

Nothing new since `v0.3.0`. The all-in-one image and the README that follows the Flux76 template are in [`v0.3.0.md`](v0.3.0.md); the rest in [`v0.2.0.md`](v0.2.0.md).

## 🐛 Fixed

- **Letting the worker mount an SMB share always failed** (#37). Reported on Home Assistant; the scan ended with `scan.failed` and `Unable to set current process capabilities: Operation not permitted`. `mount.cifs` sets its own privileges at start-up and asks for `CAP_SYS_ADMIN`, `CAP_DAC_READ_SEARCH` and `CAP_DAC_OVERRIDE`; if one is missing it stops before anything is mounted. Docker's default set has `CAP_DAC_OVERRIDE` but not `CAP_DAC_READ_SEARCH`, and the Compose worker drops every privilege, so a container given only `SYS_ADMIN`, as the guide said, could never mount SMB. Now `docker-compose.mounts.yml` gives the worker all three, the error message names the missing privileges instead of pointing to an override you already use, and the all-in-one image warns in the log when privileges are missing. NFS was not affected.
  - **What was tested:** with the image's real `mount.cifs` (Alpine 3.20, `cifs-utils` 7.0), the mount gets past its privilege check with the privileges of the override file and not with `SYS_ADMIN` alone; CI checks that on every build. **Not tested** is a real SMB server or a real Home Assistant installation; whether the mount then succeeds depends on the server, the version and the credentials, and on hosts with AppArmor the mount itself may still be blocked (see *Upgrade notes*). Test a new share with *Scan now*.

## 📄 Docs / Internal

- `docs/deploy.md`, both READMEs, [ADR 0013](../adr/0013-all-in-one-image.md), the OpenAPI description and the text in the interface now say what SMB needs; the claim that route (a) is "tested up to the privileges" is replaced by what was measured (#37).
- New checks in CI: a test of the privilege list of the override file, a step that runs the real `mount.cifs` with the privileges read from the merged Compose configuration, and an extension of the all-in-one image's smoke test. Each of them fails when a privilege is taken out (#37).

## ⚠️ Upgrade notes

- **Are you running `0.2.0` or `0.3.0` and do you not let the worker mount NFS/SMB?** Then there is nothing to do: nothing changes in `docker-compose.yml`, `.env.example` or the database, and there are no new migrations. Pull the image (`docker compose pull`, then `docker compose up -d`; *Redeploy* in a stack manager does not fetch a moving tag by itself).
- **Do you use `docker-compose.mounts.yml` (the worker mounts itself)?** Get the new version of that file and recreate the worker with `docker compose -f docker-compose.yml -f docker-compose.mounts.yml up -d`. If you have your own copy, add `DAC_READ_SEARCH` and `DAC_OVERRIDE` under `worker.cap_add` next to `SYS_ADMIN`. Without those two SMB keeps failing; NFS already worked.
- **Do you run the all-in-one image or a container with `docker run` (Unraid, Portainer, Home Assistant) and want the worker to mount SMB?** Give the container `--cap-add SYS_ADMIN --cap-add DAC_READ_SEARCH`; Docker's default privileges stay, so `DAC_OVERRIDE` needs no separate flag. Where AppArmor blocks the mount, add `--security-opt apparmor=unconfined`. The safer route remains: mount the share on the host and pass it read-only (see [`docs/deploy.md`](../deploy.md#2-shares-beschikbaar-maken), in Dutch).
- **Coming from before `0.2.0`?** Then first do the update steps of [`v0.2.0.md`](v0.2.0.md) (the heading *Upgrade notes*). In short: take a backup (migrations `0005`, `0006` and `0007` cannot be undone), rename the variables with `sed -i 's/^NASA_/NASSA_/' .env` (an old `.env` is refused), move the database from the volume `db-data` to an absolute folder `DATA_PATH` with `scripts/migrate_data.sh`, and replace your `docker-compose.yml` with the one of this version.
- **Want to try the all-in-one image?** See [`docs/deploy.md` §8b](../deploy.md#8b-all-in-one-image-unraid-store-en-home-assistant). The package `nas-storage-analyzer-aio` may need to be made public on GHCR once before Unraid or Home Assistant can pull it without signing in.
